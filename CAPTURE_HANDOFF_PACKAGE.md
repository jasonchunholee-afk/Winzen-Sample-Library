# Winzen Sample Library - Capture (Photo Station Standalone Spec & Code Package)

Welcome to the **Winzen Sample Library - Capture** module. This package provides the comprehensive architecture, business rules, API contracts, local storage layout, and complete starter source code for the standalone Capture Station applet.

---

## 1. System Vision & Persona Responsibilities

### **User Roles & Authority Rules**
1. **Chen (Photo Booth Operator):**
   - **Zero Typing Workflow**: By default, Chen does NOT type garment names or manually enter codes. Garment barcodes or physical tags are scanned, or presets are tapped.
   - **Zero Authority Over Overwrites**: Chen cannot rename active catalog items or resolve duplicate naming collisions.
   - **Missing Label Protocol**: If a garment arrives with no label or barcode, Chen clicks the **"Missing / Untagged Label"** button. The system automatically creates a timestamped prototype code:
     `UNTAGGED-YYYYMMDD-XX` (e.g., `UNTAGGED-20260916-01`).
   - A quick information tag form is presented to capture any quick notes if available, but does not block shooting.

2. **Jennifer (Senior Technical Merchandiser):**
   - Holds 100% naming, approval, and duplicate-handling authority.
   - All `UNTAGGED-*` items and naming discrepancies appear in Jennifer's **Review / Discrepancy Queue** in the Main application for identification or manual tagging.
   - Jennifer flags poor quality / unfocused photos for retake in Main. These are pulled by Capture via the `/api/capture/retake-queue` endpoint.

## 2. Operating Modes: Dual Online & Offline Architecture

### **Local Storage Hierarchy (Offline Mode)**
When running offline at the photography rig, Capture writes to three local subfolders:
```
/winzen_capture_data/
  ├── raw/          # Uncompressed high-resolution master camera archives (10-30MB)
  ├── ai/           # 1024px token-optimized JPEG (quality: 85) for Gemini OCR
  └── thumb/        # 400px progressive JPEG (quality: 80) for instant grid rendering
```

### **Push Models**
1. **Online Mode (Instant Stream)**:
   - As shots are captured, they are pushed immediately either image-by-image or as a garment set to Main via `POST /api/upload` (or `/api/upload-chunk` for chunked resumable transfers).
2. **Offline Batch Sync**:
   - Operator shoots an entire cart/batch offline.
   - When network connectivity is established, operator triggers **"Folder Sync"**.
   - Because `raw/`, `ai/`, and `thumb/` are already pre-compressed locally, Main accepts the multi-part payload without requiring server re-compression.

## 3. Filename & Suffix Naming Contract

Filenames generated by Capture must conform to:
`[GARMENT_ID]_[ROLE_OR_SUFFIX]_[TIMESTAMP].jpg`

- **Garment ID**: Standard Winzen alphanumeric code (e.g., `20S-1004-2`, `18S-1859-1`) or `UNTAGGED-YYYYMMDD-XX`.
- **Timestamp**: 10-13 digit epoch milliseconds or Unix timestamp (e.g., `_1726481920`). Main's parser automatically detects and strips this timestamp to determine the base identity while preserving uniqueness.

### **Shot Taxonomy & Presets**
| Category | Shot Label | Suffix | Required |
| :--- | :--- | :--- | :--- |
| **Standard Tops/Pants** | Front View | `(F)` or `_Front` | Yes |
| | Back View | `(B)` or `_Back` | Yes |
| | Spec/Care Label | `_Label` or empty | Yes |
| **Jackets / Outerwear** | Front (Closed) | `_Front_Closed` | Yes |
| | Front (Open/Lining) | `_Front_Open` | Yes |
| | Back View | `_Back` | Yes |
| | Inside Lining | `_Inside_Lining` | Optional |
| **Reversible** | Side A Front / Back | `_SideA_Front`, `_SideA_Back` | Yes |
| | Side B Front / Back | `_SideB_Front`, `_SideB_Back` | Yes |
| **2-Piece Sets** | Top Front / Back | `_Top_Front`, `_Top_Back` | Yes |
| | Bottom Front / Back| `_Bottom_Front`, `_Bottom_Back`| Yes |
| **Detail Presets** | Collar / Pocket / Macro | `_Detail_Collar`, `_Detail_Pocket` | Optional |

## 4. Main Applet Integration Endpoints

All coordination between Main and Capture occurs through standard HTTP endpoints. Capture does not need hardcoded rules:

### 1. Taxonomy Sync
- **`GET /api/config/taxonomy`**
- Returns all categories, shot presets, required flags, and suffix naming rules. Capture caches this locally for offline use.

### 2. Retake Worklist Queue
- **`GET /api/capture/retake-queue`**
- Returns all garments flagged with `needs_reshoot` by Jennifer, along with specific reasons (e.g. "Blurry care label") and target angles.

### 3. Image Upload
- **`POST /api/upload`** (Multi-part form with `image`, `thumb`, `ai`, `garmentId`, `role`)
- **`POST /api/upload-chunk`** (Resumable chunked upload with slice verification)

## 5. Ready-to-Use Capture Client Implementation

Below is a complete, lightweight TypeScript service module that Capture can drop directly into its codebase:

```typescript
// winzenCaptureClient.ts

export interface CaptureShot {
  blob: Blob;
  role: 'Front' | 'Back' | 'Label' | 'Detail';
  suffix: string;
  garmentId: string;
  timestamp: number;
}

export class WinzenCaptureClient {
  private mainApiUrl: string;

  constructor(mainApiUrl = 'http://localhost:3000') {
    this.mainApiUrl = mainApiUrl;
  }

  // 1. Sync Taxonomy
  async fetchTaxonomy() {
    const res = await fetch(`${this.mainApiUrl}/api/config/taxonomy`);
    if (!res.ok) throw new Error("Failed to fetch taxonomy");
    return res.json();
  }

  // 2. Fetch Retake Worklist for Chen
  async fetchRetakeQueue() {
    const res = await fetch(`${this.mainApiUrl}/api/capture/retake-queue`);
    if (!res.ok) throw new Error("Failed to fetch retake queue");
    return res.json();
  }

  // 3. Generate Untagged Prototype Code (Missing Label)
  generateUntaggedCode(): string {
    const dateStr = new Date().toISOString().slice(0, 10).replace(/-/g, '');
    const rand = Math.floor(10 + Math.random() * 90);
    return `UNTAGGED-${dateStr}-${rand}`;
  }

  // 4. Push Shot to Main
  async uploadShot(shot: CaptureShot, thumbBlob?: Blob, aiBlob?: Blob) {
    const formData = new FormData();
    const filename = `${shot.garmentId}_${shot.suffix}_${shot.timestamp}.jpg`;
    
    formData.append('image', shot.blob, filename);
    if (thumbBlob) formData.append('thumb', thumbBlob, filename);
    if (aiBlob) formData.append('ai', aiBlob, filename);
    formData.append('garmentId', shot.garmentId);
    formData.append('role', shot.role);

    const res = await fetch(`${this.mainApiUrl}/api/upload`, {
      method: 'POST',
      body: formData
    });
    return res.json();
  }
}
```

## 6. Coordinated Labelling Rule: Online Temporary Naming & Main OCR Renaming

### The Problem
When the **Capture Station** is running (online or offline), there is **no AI/OCR model** running at the camera booth rig to process the physical care label text. The operator (Chen) cannot and should not type style codes manually (strictly following the **Zero Typing Mandate**).

### The Coordinated Solution
1. **Capture Generates Temporary Identifier**:
   - When shooting without a pre-scanned barcode, Capture generates a coordinated temporary identifier:
     - Pattern: `TEMP-YYYYMMDD-HHMMSS-XX` (or `UNTAGGED-YYYYMMDD-XX`)
     - Example: `TEMP-20260916-143022-01`
   - Image filename syntax:
     - Front view: `TEMP-20260916-143022-01 (F).jpg` (or `TEMP-20260916-143022-01_Front_[TIMESTAMP].jpg`) -> `role: 'Front'`
     - Back view: `TEMP-20260916-143022-01 (B).jpg` (or `TEMP-20260916-143022-01_Back_[TIMESTAMP].jpg`) -> `role: 'Back'`
     - Label view: `TEMP-20260916-143022-01.jpg` (or `TEMP-20260916-143022-01_Label_[TIMESTAMP].jpg`) -> `role: 'Label'`
2. **Online Streaming / Ingestion**:
   - Capture streams each shot via `POST /api/upload`:
     - `formData.append('image', rawBlob, filename);`
     - `formData.append('thumb', thumbBlob);`
     - `formData.append('ai', aiBlob);`
     - `formData.append('garmentId', tempGarmentId);`
     - `formData.append('role', role);`
     - `formData.append('enableOcr', role === 'Label' ? 'true' : 'false');`
3. **Main Automated Renaming Engine**:
   - Main stores the temporary record and places files in `images/`, `images_thumb/`, `images_ai/`.
   - When the `role: 'Label'` shot is received, Main's server-side background Gemini OCR worker runs OCR extraction.
   - Upon successfully identifying `y_style_no` (e.g. `20S-1004-2`) or `cust_style_no`:
     - Main automatically renames the garment record from `TEMP-20260916-143022-01` to `20S-1004-2`.
     - Main renames all associated image files on disk across `images/`, `images_thumb/`, and `images_ai/`.
     - Main updates the database records in `images`, `garments`, and `summaries`.
     - An audit note is logged: `Auto-renamed from Capture temporary code TEMP-... after label OCR extraction`.
   - Merchandisers can also manually rename or approve style codes via `POST /api/garments/:id/rename-garment`.

## 8. Future Re-Integration & Shared Architecture Guarantee

To ensure both applications can seamlessly merge back into a single unified monorepo or desktop suite in the future:
1. **Design System & Styling**: Both applications use identical Tailwind CSS 4 utility classes, neutral-950 dark theater styling for camera feeds, and Lucide icons.
2. **Component Interface**: The Capture Station lives entirely inside `src/components/Capture.tsx` with sub-components under `src/components/capture/`.
3. **Shared Contracts**:
   - `src/config/garmentShotTaxonomy.ts` defines taxonomy, categories, and suffix rules.
   - `src/utils/imageCompression.ts` defines the 3-tier client-side pre-compression pipeline (`rawBlob`, `thumbBlob`, `aiBlob`).
   - `src/utils/fileParsing.ts` defines the unified regex parser supporting `TEMP-*` and `UNTAGGED-*`.
4. **Code Export Options in App Bar**:
   - **"Export Capture Module"** (`/api/export-capture`): Downloads the isolated Capture subsystem (`Capture.tsx`, `capture/`, taxonomy, compression, handoff spec).
   - **"Export Full App"** (`/api/export-code`): Downloads the complete codebase with all Main Review, Library, AI parsing, and Cloud database engines.

## 9. Agent Interaction Syntax & Macros ([Optimisation] and [Reflect])

To maintain rapid development velocity, prevent runtime bloat (such as WebRTC memory leaks, unoptimized canvas redrawing, and massive DOM image queues), and synchronize AI coding behaviors across both the Main and Capture sessions, the Capture Session implements the standardized `[Optimisation]` and `[Reflect]` macros in its root `AGENTS.md`.

### **Capture AGENTS.md Directives Block**
```markdown
# AGENT INTERACTION SYNTAX & MACROS

## 1. [Optimisation] Pre-Execution Analysis Macro
* **Purpose**: Pre-execution architectural and performance analysis before making any code modifications in the Capture Station.
* **Usage**:
  ```
  [Optimisation]
  ***
  <Feature Request or Refactor Description>
  ***
  ```
* **Strict Behavioral Rule**:
  - The Agent **MUST NOT write application code** or edit files during an `[Optimisation]` turn.
  - The Agent **MUST return an Execution Strategy** containing:
    1. **Agent Time / Complexity Estimate**: Anticipated tool calls and potential failure points.
    2. **Capture App Runtime Bloat Risks**: Specific analysis of camera stream canvas leaks, blob memory retention, redundant video stream re-renders, uncompressed file buffers, and DOM list overhead in Chen's rapid shooting workflow.
    3. **Existing Codebase & Protocol Verification**: Ensuring proposed changes do not break hardware pedal mapping (`TOP_*`, `MACRO_*`), 3-tier compression (`raw`, `ai`, `thumb`), or `WZ-*` sticker verification contracts.
    4. **Prompt Splitting Strategy**: A sequence of **2 to 4 distinct, atomic prompts** for the user to paste back sequentially, ensuring clean, verifiable micro-steps.

## 2. [Reflect] Post-Execution Evaluation Macro
* **Purpose**: Post-execution reflection to track latency discrepancies, analyze tool call efficiency, and refine execution plans.
* **Usage**:
  - **Variant 1 (After an [Optimisation] prompt)**: Reflects on discrepancies between estimated vs. actual analysis time, prompting precision, and split-prompt quality.
  - **Variant 2 (Standalone / Post-Build)**: Evaluates why a build or coding step took extra tool iterations or failed edits, and recommends immediate workflow optimizations.
* **CRITICAL TIME TRACKING RULE**:
  - As an LLM, the Agent does not have native access to exact wall-clock execution times for past turns.
  - The Agent **MUST NOT hallucinate or guess** the actual time taken (e.g., never invent "took 85 seconds").
  - To reflect accurately, the Agent must rely strictly on execution times explicitly provided by the user. If the user does not supply an exact duration, the Agent must focus purely on the **number of tool calls, failed edits/lints, and architectural complexity** rather than inventing a numerical duration.
```
